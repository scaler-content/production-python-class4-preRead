2. The big idea: a run that finishes is not a run you can trust

Imagine a teacher who reads out 40 names, but one attendance card slipped under the desk. The register says 39 present. It looks complete, and nothing says one card was not read. A batch of data can behave the same way: it ends with no error, and still lost a row.

Here is a real line from the class files. The date is written day first, so the program cannot tell if it means 7 March or 3 July:

One row of the failure file
C-3003,O-7003,SHIPPED,07/03/2025

A careless program guesses, and the guess looks exactly like a fact in the report. A careful program sets the row aside with a reason and says so. Class 4 builds the careful one, and it keeps three promises.

5. Four kinds of failure, four outcomes

A problem with data is not one thing. If every problem is treated the same way, a program either stops too often or hides too much. So we sort problems into four kinds, and each kind gets its own planned outcome.

Four words for reacting to a problem

Python has four small words for this. Read the example from top to bottom, and notice what each word is for.

try, except, else and finally
try:
    promised = read_promised(row["promised_date"])   # the line that might fail
except ValueError:
    return "quarantined: promised_date is not a date"   # runs only on that error
else:
    return f"accepted, due {promised.isoformat()}"      # runs only if try succeeded
finally:
    print(f"checked {row['case_id']}")                  # runs every time
Making tea Try: boil the water. Except: if the gas runs out, use the kettle. Else: if nothing went wrong, add the tea leaves. Finally: switch off the stove, every time.

You will also write your own error names, such as MalformedRecord and MissingSource, so the program can tell the kinds apart. That takes only a few lines each.

6. Count every row, and name every batch

A quarantine is a list of the rows the program refused. Each entry keeps the file, the line number, a category, a reason and the row exactly as it was read. A person opens the file, goes to that line and fixes it. It is a worklist, not a bin.

Then the program does the sums. Every row read must end up in one of two places, so accepted plus quarantined must equal the rows in the file. It also halts the whole batch if more than 5 percent of a file is quarantined, because that usually means the file itself is broken.

A name that never changes

Every batch gets a batch ID made from its files and settings, such as B-1bf9b12a0999. The same files and settings always give the same ID, so the program can tell when it has already finished a batch. Every run also gets its own attempt ID, and a log line. Run the same batch twice, and the second run says reused finished batch; no work repeated.

Like a train booking reference Check your booking ten times and it is still one reference, and still one seat. Each check is an attempt. The booking is one.

7. Retries, and a model that may not answer

Some failures fix themselves

A server is busy for a moment, or a message is lost. Waiting and trying again often works. But a retry needs a limit and a wait that grows, or it makes a busy service busier. Each wait is a random time up to a ceiling that doubles after every failure and stops at a cap. The randomness is called jitter, and it stops everyone retrying at the same second.

Attempt123456
Longest wait, in seconds0.512488

And one question decides everything: could a later try succeed? A timeout, a rate limit or a server error: yes. A missing key: never.

The rules for the model in Class 4

Never invent an answer

If the model cannot answer, the suggestion says UNAVAILABLE and why. It never falls back to a recorded answer, because a recorded answer is test data.

The facts stay

Whether a case needs attention comes from the rules. A failed model call never removes a flagged case from the report.

One retry layer only

If two layers each retried three times, one failure would become nine calls. So only our own retry code retries.

Cache good answers only

A good reply can be reused later. A timeout is never saved, or it would be replayed as if it were true.

Never paste a key into chat The rule from Class 3 still holds. You can do the whole class without a key, because every failure is simulated.
